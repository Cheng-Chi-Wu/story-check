## 總判定（Verdict）

**計算引擎的算術是乾淨的；出問題的是規範版本與輸入防線。**

- 我獨立重算的 300 項檢核與工具輸出**零不一致**——扭轉比、軟弱層 r1/r3、§12.3.2.2 例外判定、放大變位、SDC E/F 禁止條件、÷ρ，全部與 `PROJECT_REVIEW.md` 所述邏輯相符。三棟範例埋入的狀況（5 層 Story2 扭轉 1.30、15 層 Story1 勁度減半 + Story4 扭轉 1.50、30 層 Story12 勁度 55% + Story20 扭轉 1.55）都被正確抓出。
- 但工具實作的是 **ASCE 7-16 的扭轉不規則框架（Type 1a/1b），卻標示為 ASCE 7-22**。7-22 已改採 TIR（Torsional Irregularity Ratio）單一型定義，並新增「強度分布」觸發條件——這是整份報告最嚴重的一項（Finding 1）。
- 解析器對真實 ETABS 匯出檔的第一道防線有破口：標題列會讓 CSV 解析直接吐出 pandas 原始錯誤（Finding 2）；退化數據（平均變位 = 0）會讓檢核**靜默消失**而不是報錯（Finding 4）。
- Word 計算書的公式代入呈現是真的好，離送審可用只差「設計依據與假設」這一頁的完整性（Finding 6），以及上述規範框架問題。

**現階段定位**：事務所內部的快速複核工具——合格；對外宣稱「ASCE 7-22 檢核」並產生送審計算書——尚未到位。修 Finding 1、2、4 的成本都不高，但不修，產品的核心承諾（7-22、送審）就是空的。

## 四、Word 計算書審查（任務 4）

**洛杉磯的審圖者會收嗎？** 以「EOR 簽章背書的輔助計算附件」形式：**大體可以**——公式代入、條文出處、被標記項目的彙總表、逐層明細、簽核欄與印章欄、免責聲明，該有的骨架都有，而且公式代入的寫法（例如 `Delta = C_d * Delta_e / I_e = 5.5 * 0.664 in / 1 = 3.650 in [center of mass (avg)]`)正是審圖者要看的東西。這份計算書的呈現品質高於多數事務所的內部試算表。

以「獨立送審計算書」形式：**還不行**，缺的是依據與可追溯性，不是排版：

1. **設計依據不自足**（Finding 6):I_e、樓板型式、偶發扭矩前提、分析方法都缺。審圖者光看這份文件，無法重建檢核成立的條件。
2. **規範框架是 7-16 的**（Finding 1)：標題寫 ASCE/SEI 7-22，內容引用 Type 1a/1b——熟悉 7-22 的審圖者第一眼就會退件要求說明。
3. **WARNING 的後果沒寫**（Finding 3)：計算書是給 EOR 和審圖者做決定的文件，只寫「存在但允許」而不寫「因此設計必須做 X」，等於把最關鍵的資訊留在文件外。
4. 細節：日期差一天（F11)、PASS 列誤標 Type 1a(F10)、被跳過的檢核不留痕（F9)。
5. 未驗證：`project_info` 有 `project_number`、`company`、`engineer` 等欄位，但範例沒給值，我無法確認填了之後計算書的呈現（專案編號是否出現在每頁頁首等）。建議自測一次。

## 五、產品觀點（任務 5 + §11 問題 10–13)

**痛點存在，但比你們想的窄。** 不規則 + 變位檢核是整個耐震計算書裡很小、很後段的一塊。多數事務所現況是：ETABS 本身就輸出 Story Stiffness / Max-Avg Drifts，工程師用內部 Excel 模板做判定——模板一次寫好、之後每案複製，邊際成本接近零。ETABS 的後處理（以組合工況放大 C_d/I_e 再讀變位）也能直接給設計變位。真正沒被滿足的不是「算」，是「**整理成審圖者能讀的計算書**」——這恰好是你們做得最好的部分，也是 Finding 1/3/6 所在的部分。結論：產品的價值在報告，不在引擎；報告的可信度就是產品本身。

**誰付錢？** 個人工程師為三項檢核付訂閱費的意願低（免費替代品太多）。事務所層級有可能——前提是產出能活過一輪 plan check correction cycle。建議的驗證順序不是加功能，是找 3–5 位友善的 SE 用**真實 ETABS 匯出檔**跑一遍：解析器從未見過真實檔案（你們自承），而 Finding 2 顯示第一道門就可能倒。這是目前存亡等級最高的風險，高於任何功能缺口。

**沒有 PE/SE 背書的工具能不能賣？** 結構軟體本來就都是這樣賣的（ETABS 也不替你蓋章），EOR 蓋章負責是常態，免責聲明有寫是對的。但行銷文案若宣稱「ASCE 7-22 compliant」而框架落後一版，那就是廣告不實等級的曝險——先修框架，或先改文案，二選一，要在第一個付費用戶出現之前完成。

**只做三項檢核夠不夠？**（§11 Q6）對「快速複核」夠；對「送審計算書」不夠，審圖者下一個會問的是：弱層（Type 5a/5b，需要樓層強度，是另一張 ETABS 表）、P-Δ 穩定係數（§12.8.7)、樓板變形檢核。缺弱層是最痛的——它和軟弱層是同一個 Table 12.3-2 的姊妹項，文件齊全度上很難解釋為什麼只有一半。這應該是功能路線圖的第一名，排在其他水平不規則之前。

其餘 §11 問題的答案散見上文：Q1 → 第二節；Q2 → 第二節（可辯護，建議揭露解讀）；Q3 → 第二節（可辯護）；Q4 → 用 ETABS Story Stiffness 做軟弱層判定是實務常見作法，但勁度隨工況而變是它的原罪，計算書應逐方向註明勁度採用的工況（目前只有變位工況清單）；Q5 → 燈號本身清楚，問題在 WARNING 的文字不列後果（F3);Q7 → F4/F5 是實測到的邊界錯誤，浮點門檻邊界未測；Q8 → F13 實測證實；Q9 → 兩個契約層面的味道：檢核「消失」而非回報 N/A 狀態（F4/F9 同源）、`max_dc_ratio` 混種（F12）——把 check 狀態擴成 PASS / WARNING / FAIL / NOT_APPLICABLE（附原因），兩個問題一起解。
